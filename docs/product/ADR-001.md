# ADR-001 — Direção técnica do BarberFlow IA

**Data:** 2026-10-28  
**Status:** proposto, sujeito à revisão antes da implementação.

## Contexto

O repositório atual é um Next.js App Router com landing page e formulário demonstrativo. O produto futuro requer gravação segura de reservas, chatbot, campanhas de reativação, n8n e possível operação SaaS para múltiplas barbearias.

## Decisões propostas

1. **Monólito modular Next.js + Route Handlers inicialmente.** Manter front e servidor próximos, sem criar NestJS/Express paralelo no MVP. Domínios separados para extração posterior, se necessária.
2. **PostgreSQL + Prisma para persistência.** A aplicação calcula slots; PostgreSQL garante restrição de intervalos sobrepostos para reservas confirmadas, via migration SQL quando a capacidade de schema Prisma não bastar.
3. **IA é camada de conversa e interpretação, nunca autoridade de agendamento.** O servidor confere permissões, parâmetros e confirmação antes de chamar `BookingService`.
4. **n8n coordena automações, não guarda estado canônico.** API fornece candidatos válidos, controla consentimento, frequência, idempotência e auditoria.
5. **Piloto de uma barbearia com tenantId desde o modelo.** Reduz escopo operacional, mas previne reescrita e vazamento óbvio na futura evolução.
6. **Chat web primeiro como menor caminho de prova da IA; WhatsApp oficial em etapa posterior.** Se operação da barbearia exigir WhatsApp já no piloto, replanejar dependência sem comprometer backend comum.
7. **Planos de serviços ao consumidor ≠ planos SaaS da barbearia.** Separar nomes e entidades antes da cobrança.

## Alternativas avaliadas

| Alternativa | Benefício | Motivo de não escolher agora |
|---|---|---|
| Next.js + NestJS desde o início | Serviço dedicado e divisão explícita | Mais deploys/contratos/autenticação para um time pequeno |
| Agendamento inteiramente no n8n | Prototipagem rápida | Dificuldade de garantir transações e regras canônicas |
| IA com acesso direto ao SQL | Flexibilidade do modelo | Risco de dados vazados, alteração indevida e inconsistência |
| Agenda somente no WhatsApp | Canal familiar | Dependência externa, custo/política e depuração mais difícil |
| Multi-tenant completo no primeiro lançamento | Escala potencial | Atrasa validação comercial da agenda e retenção |

## Consequências

**Positivas:** MVP menor, aproveitamento do projeto, API única para site/chat/WhatsApp, fácil testar a reserva e desligar IA em falha.  
**Negativas:** Next.js acumula responsabilidades até exigir extração; n8n e mensageria exigem operação, observabilidade e política de retenção; migrations de restrição de intervalo exigem SQL revisado.  
**Gatilhos para revisar:** alto volume de webhooks, filas extensas, deploy independente de backend, múltiplas equipes, necessidade de calendário externo bidirecional, mudança de modelo de cobrança.

## Implementação e validação

Aprovar este ADR durante o primeiro PR de backend, documentar alterações em novo ADR, adicionar testes de concorrência e privacidade. Nenhuma decisão deste ADR foi implementada apenas porque está documentada.
